## 1. Введение и фундаментальные принципы

**NeXXUs** — это децентрализованный протокол суверенного P2P-хранения данных с нулевым разглашением (Zero-Knowledge), защитой от облачного аутсорсинга и бартерной экономической моделью, исключающей спекулятивное фермерство «из воздуха».

### Ключевые аксиомы:
1. **Ноль доверия к узлам хранения**: узлы-доноры (хранители) получают исключительно зашифрованные шарды данных. Они не могут прочитать их содержимое, модифицировать их или определить имя исходного файла.
2. **Бартер 16GB за 2.0GB**: выделяя первую базовую секцию в 16GB свободного места, пользователь получает гарантированные 2.0GB личного нерушимого приватного сейфа без необходимости покупки токенов.
3. **«За пустоту не платим»**: токены $NEX начисляются исключительно за полезные байты чужих чанков, реально удерживаемые на диске и прошедшие криптографические аудиты PoR. Зарезервированное, но не занятое пространство наград не приносит.
4. **Математическая избыточность (Многоуровневая)**:
   - **MVP-A (Android-смартфоны — по умолчанию)**: простая 6-кратная репликация (**RF=6×**) с уникальным per-node ChaCha20-Poly1305 шифрованием каждого чанка. Защищает слабый CPU мобильного телефона от перегрева матричными вычислениями над полем Галуа и гарантирует живучесть сейфа при типичном высоком оттоке ($p_{offline} \approx 0.35\text{--}0.4$).
   - **V2 / Desktop & Linux Nodes**: стирающее кодирование **Reed-Solomon (4+2)** над полем Галуа $GF(2^8)$ (4 блока данных + 2 блока четности) для серверов, десктопов и мощных одноплатников с экономией места (1.5× overhead вместо 6×).
   - **Холодный архив (Cold Archive, opt-in)**: тариф с пониженной избыточностью **RF=4×** с обязательным подтверждением пользователем риска потери объекта (~2-3%/год на мобильных нодах).

## 2. Архитектура криптографии и Zero-Knowledge

### 2.1. Иерархия ключей (BIP-39 / BIP-32)
При инициализации узла или клиентского хранилища генерируется 12/24-словная мнемоническая фраза по стандарту BIP-39. Из PBKDF2-HMAC-SHA512 сида (512 бит) деривируются независимые ветки:

```
                          [ BIP-39 Mnemonic Seed ]
                                     |
                                  m/44'/9999'/0'
                                     |
                +--------------------+--------------------+
                |                                         |
     m/44'/9999'/0'/0'/0                       m/44'/9999'/0'/1'/0
  [ Node Identity Keypair ]                 [ Vault Master Secret ]
  - P2P Public Key (nx1pk_...)              - Симметричный ChaCha20 ключ (256 бит)
  - Tor v3 .onion адрес (56 chars)          - Никогда не покидает устройство клиента
  - Подпись сообщений PoR                   - Доноры узлов не имеют к нему доступа
```

### 2.2. Сквозное шифрование ChaCha20-Poly1305 AEAD
Файлы шифруются на стороне клиента перед фрагментацией:
- Алгоритм: `ChaCha20-Poly1305` (RFC 8439) с аутентифицированными данными (AEAD).
- Размер нонса: 12 байт (96 бит), деривируется уникально под каждый индекс чанка.
- Тег аутентификации Poly1305: 16 байт (128 бит).
- **Гарантия целостности**: любая попытка подмены даже одного бита шифротекста узлом-хранителем приводит к немедленной ошибке верификации MAC и отклонению чанка.

## 3. Экономическая модель и секции хранения

### 3.1. Секции по 16GB
Дисковое пространство квантуется блоками по 16GB:
- $\text{Sections} = \lfloor \text{AllocatedStorageGB} / 16 \rfloor$.
- **Секция 1 (Базовая)**: 16GB выделяется в сеть в обмен на право хранения до 2.0GB собственных зашифрованных данных. Монетизация токенами на базовой секции отключена (Zero Greed Invariant).
- **Секции 2..N (Расширенные)**: монетизируются токенами $NEX при условии реального размещения полезной нагрузки.

### 3.2. Математика Anti-Loop Farming
Для предотвращения атаки «замкнутого цикла» (когда злоумышленник сам у себя покупает хранение для накрутки токенов):
$$\text{WriterFee} > \text{StorerReward}$$
Комиссия за запись чанка в сеть строго превышает суммарную выплату узлам за его хранение. Разница направляется на дефляционное сжигание (Burn) и в фонд аудиторов. Доходность злоумышленника от хранения собственных файлов является строго отрицательной.

### 3.3. Вестинг наград (8 недель / 56 дней)
Все начисленные награды за доказанное хранение блокируются в контракте `NexxusTreasuryVesting.fc` на 56 дней (8 полных недельных эпох). Досрочный вывод невозможен, что отсекает спекулятивные ноды-однодневки.

### 3.4. Динамическая прогрессия Сейфа и Честная деградация
- **День 1**: 0.5 GB личного сейфа.
- **День 14**: 1.0 GB личного сейфа.
- **День 45+**: максимальные 2.0 GB.
- **Честная деградация (Honest Degradation)**: если узел уходит в офлайн:
  - 1–14 дней офлайн: статус `Warning` (данные активны, выдается предупреждение).
  - 15–28 дней офлайн: урезание до 0.5 GB, прекращение новых записей.
  - 28+ дней офлайн: статус `Degraded` и запуск вытеснения (Eviction) из сети с передачей шардов активным участникам.

## 4. Стратегии избыточности: MVP-A RF=6× и V2 Reed-Solomon (4+2) Erasure Coding

Архитектура NeXXUs строго разграничивает схемы избыточности в зависимости от типа устройства и аппаратных возможностей:

### 4.1. MVP-A: Полнотекстовое зеркалирование RF=6× (Базовый стандарт для Android)
Для мобильных устройств (смартфонов), работающих на слабых ARM Cortex-A53/A55 ядрах:
- Каждый 16KB чанк реплицируется на 6 независимых узлов (**RF=6×**).
- **Уникальное Per-Node шифрование**: каждая из 6 реплик зашифрована отдельным ключом `ChaCha20(NodePubKey || ChunkSeed)`, что исключает облачный аутсорсинг (дедупликацию и хранение одной копии на стороне провайдера).
- **Нулевая вычислительная нагрузка**: мобильный телефон не тратит аккумулятор на матричные умножения в поле Галуа при записи и отдаче блоков.
- **Вероятность потери**: при типичном для старых смартфонов оттоке $p_{offline} \approx 0.35\text{--}0.4$, схема RF=6 обеспечивает расчетную выживаемость объекта $> 99.6\%$.

### 4.2. V2 Tier: Стирающее кодирование Reed-Solomon (4+2) над $GF(2^8)$ (Desktop & Linux)
Для мощных узлов (десктопы, mini-PC, серверы Ubuntu/Debian):
Каждый 16KB чанк кодируется по схеме $N=6, K=4$ (4 блока данных по 4,096 байт + 2 блока четности):

$$\begin{pmatrix} D_0 \\ D_1 \\ D_2 \\ D_3 \\ P_1 \\ P_2 \end{pmatrix} = \mathbf{G} \cdot \begin{pmatrix} D_0 \\ D_1 \\ D_2 \\ D_3 \end{pmatrix}$$

где:
- $D_0, D_1, D_2, D_3$ — 4 блока исходных данных по 4,096 байт.
- $P_1 = D_0 \oplus D_1 \oplus D_2 \oplus D_3$ — первая четность (XOR).
- $P_2 = \sum_{i=0}^3 \alpha^i \cdot D_i$ — вторая четность в поле $\text{GF}(2^8)$ с примитивным полиномом `0x11d`.

#### Восстановление при отказе:
При потере любых двух шардов из 6 формируется усеченная матрица 4×4 из выживших строк. Выполняется обращение матрицы методом Гаусса-Жордана в $\text{GF}(256)$ через предрасчитанные таблицы `GF_EXP` и `GF_LOG`. Исходный 16KB чанк восстанавливается **бит-в-бит со 100% точностью**, экономя дисковое пространство (оверхед всего 1.5× вместо 6×).

### 4.3. Архивный холодный тариф RF=4× (Opt-In)
Специальный тариф со сниженным коэффициентом репликации (RF=4) доступен исключительно по явному согласию пользователя с предупреждением о риске потери ~2–3%/год при сохранении архивов на смартфонах.

## 5. Anti-Outsourcing Proofs & Мониторинг топологии ASN

### 5.1. Физическая отсечка локального I/O (120 мс)
Чтобы исключить перепродажу хранения в Amazon S3, Google Cloud или IPFS:
- Локальное чтение с NVMe/SSD/eMMC при вызове PoR выполняется за 5–45 мс.
- Запрос, перенаправленный через прокси в удаленное облако, неизбежно требует сетевого раундтрипа и авторизации (> 180–350 мс).
- Порог `LOCAL_IO_CUTOFF_MS = 120 ms`. Ноды, превысившие задержку, дисквалифицируются.

### 5.2. Канареечные ловушки (Canary Traps)
В каждый 16-й раунд проверки встраивается скрытый канареечный чанк с детерминированным сидом. Неверный ответ или просрочка тайм-аута приводят к автоматическому слэшингу залога узла.

### 5.3. Индекс концентрации ASN (HHI)
$$\text{HHI} = \sum_{i=1}^M \left( \frac{\text{Replicas in } \text{ASN}_i}{\text{Total Replicas}} \times 100 \right)^2$$
- $\text{HHI} < 2500$: **EXCELLENT** (шарды распределены по независимым провайдерам: Cloudflare, Hetzner, OVH, домашние ISP).
- $\text{HHI} \ge 4000$: **CONCENTRATED** (опасная концентрация в одном дата-центре, автоматическое перераспределение шардов).

### 5.4. Автономное самоисцеление (Self-Healing Loop)
При падении числа активных шардов ниже 6 (или при выходе ноды из строя) демон самоисцеления:
1. Запрашивает 4 любых здоровых шарда.
2. Решает систему уравнений Reed-Solomon.
3. Генерирует недостающий шард.
4. Отправляет его на новую ноду в ранее незадействованной автономной системе (ASN).

## 6. Kademlia 256-bit DHT и сетевой Wire-протокол

### 6.1. Метрика XOR
Расстояние между узлом $x$ и ключом $y$:
$$d(x, y) = x \oplus y$$
256-битные идентификаторы раскладываются по 256 $k$-карманам ($k=20$).

### 6.2. Защита от Sybil-атак (PoW Nonce)
Каждая нода при объявлении в DHT обязана предъявить криптографическое доказательство работы (Proof-of-Work), привязанное к её NodeID и Tor .onion адресу:
$$\text{SHA-256}(\text{NodeID} \parallel \text{OnionAddress} \parallel \text{Nonce}) < \text{Target}$$

- **Тестовый и CI стенд (`test/protocol.test.ts`)**: калиброванная сложность `14 ведущих нулевых бит` (выполняется за 5–25 мс в V8 движке). Это гарантирует мгновенный запуск тестов без задержки сборочного конвейера.
- **Мобильный Mainnet (Android смартфоны)**: целевая сложность составляет **18–20 бит** (или 64K раундов Argon2id / PBKDF2), что требует **30–60 секунд непрерывной работы CPU** на мобильном процессоре (ARM Cortex-A53). Это делает атаку перебором идентификаторов (ID-grinding и Kademlia Eclipse) экономически и энергетически нерентабельной для спамеров и ботнетов.

### 6.3. Бинарный фрейминг сокетов
- `Magic Bytes`: `0x4E58` (ASCII "NX").
- `Opcode` (1 байт):
  - `0x01`: `PING`
  - `0x02`: `PONG`
  - `0x10`: `STORE_CHUNK` (сохранение 16KB чанка)
  - `0x11`: `GET_CHUNK`
  - `0x20`: `POR_CHALLENGE`
  - `0x21`: `POR_RESPONSE`
  - `0x30`: `KAD_FIND_NODE`
  - `0x31`: `KAD_NODES_FOUND`
- `Flags` (1 байт).
- `RequestId` (4 байта, big-endian uint32).
- `PayloadLength` (4 байта, big-endian uint32).
- `Payload` (переменный размер).

## 7. Proof-of-Retrievability (PoR) и дерево Меркла

1. Каждый файл индексируется деревом Меркла: листья — $\text{SHA-256}(\text{Chunk}_i)$.
2. Корень дерева ($\text{Merkle Root}$) фиксируется при загрузке.
3. Аудитор отправляет вызов: `Seed` (256 бит энтропии) и `ChunkIndex`.
4. Нода-донор обязана вернуть:
   $$\text{Response} = \text{SHA-256}(\text{Seed} \parallel \text{ChunkData})$$
   вместе с ветвью доказательства Меркла (Merkle Audit Path).
5. **Тайм-аут**: ответ должен поступить строго в течение **3000 мс**.

## 8. Смарт-контракты TON (FunC)

В каталоге `/contracts` размещены исходные коды проверенных смарт-контрактов для блокчейна The Open Network (TON):

1. **`NexxusEpochController.fc`**:
   - Управляет 24-часовыми суточными эпохами сети.
   - Фиксирует кворум доказательств PoR от аудиторов.
   - Передает подтвержденные объемы хранения в казначейство.

2. **`NexxusTreasuryVesting.fc`**:
   - Принимает эмиссионные пулы токенов $NEX.
   - Рассчитывает 8-недельный график разлока (56 дней).
   - Предотвращает несанкционированный вывод невестированных средств.

3. **`NexxusAuditorCouncilBond.fc`**:
   - Управляет залогами (Bond) нод-аудиторов.
   - Применяет слэшинг за ложные репорты или сговор.

## 9. Развёртывание Linux-демона и systemd

Стек Linux-демона NeXXUs спроектирован в двух взаимодополняющих режимах исполнения:

### 9.1. Архитектура демона (TypeScript Core + esbuild Bundle + .deb)
1. **Исходный код (`scripts/linux-daemon.ts`)**: полностью типизированный TypeScript-демон, реализующий сетевой P2P-стек (Kademlia DHT, бинарный сокетный протокол с заголовком `0x4E58`, хранение 16KB чанков на локальном диске, PoR-ответы за <3000 мс и замеры блочного I/O).
2. **Режим разработки (Development Mode)**: быстрый запуск без фазы компиляции с помощью интерпретатора `tsx`:
   ```bash
   # Статус узла
   npx tsx scripts/linux-daemon.ts status
   # Бенчмарк диска
   npx tsx scripts/linux-daemon.ts benchmark
   # Проверка PoR
   npx tsx scripts/linux-daemon.ts test-por
   ```
3. **Режим промышленного деплоя (Production .deb + systemd)**:
   - Сборка автономного CJS-бандла: `npm run bundle:daemon` с помощью `esbuild` собирает весь код демона вместе со всеми внешними зависимостями в один файл `dist/nexxusd.cjs` (252 КБ).
   - Сборка установочного пакета: `npm run deb:build` (скрипт `scripts/build-deb.sh`) упаковывает бандл, файл конфигурации `/etc/nexxus/nexxus.conf`, глобальный лаунчер `/usr/bin/nexxusd` и systemd-юнит в стандартный Debian-пакет `nexxus-node_2.0.0_amd64.deb` (размер сжатого архива **~51 КБ**).
   - Зависимости пакета: требует установленного рантайма `nodejs >= 18.0.0` на хосте.

### 9.2. Установка .deb пакета на Ubuntu / Debian Server
```bash
# 1. Установка пакета через dpkg
sudo dpkg -i public/packages/nexxus-node_latest_amd64.deb

# 2. Подтягивание зависимостей (если на сервере еще нет nodejs >= 18)
sudo apt-get install -f -y

# 3. Активация и запуск системного сервиса systemd
sudo systemctl enable --now nexxus-node

# 4. Проверка журнала событий
sudo journalctl -u nexxus-node -f
```

### 9.3. Конфигурация systemd (`/etc/systemd/system/nexxus-node.service`)
```ini
[Unit]
Description=NeXXUs Sovereign P2P Decentralized Storage Daemon
Documentation=https://nexxus.network
After=network.target network-online.target
Wants=network-online.target

[Service]
Type=simple
User=nexxus
Group=nexxus
EnvironmentFile=-/etc/nexxus/nexxus.conf
ExecStart=/usr/bin/nexxusd serve
Restart=always
RestartSec=3s
LimitNOFILE=1048576
StandardOutput=journal
StandardError=journal
SyslogIdentifier=nexxusd

# Linux Security Sandboxing
ProtectSystem=full
ProtectHome=read-only
PrivateTmp=true
NoNewPrivileges=true
```
